Model Deep-Dive

A closer look at the three machine-learning models inside AI_match_stats_prediction.py — plus the outcome-probability conversion layer that turns BART's goal difference into Win / Draw / Loss. Written for someone new to the topic.

Model 1

GBR — Gradient Boosting Regressor

Predicts the in-game statistics (xG, shots, possession…) before a match is played, so the General signal has something to work with.

What problem is it solving? Before kick-off we don't know a match's in-game stats — but the General signal needs them. The GBR's whole job is: "Given only what we know before kick-off (team form, head-to-head, player strength, weather), make an educated guess of what the in-game stats will be." It is a regressor, meaning it predicts a number (like "14.2 shots"), not a category like win/lose.

The idea behind Gradient Boosting (simple version)

Start with a decision tree. A decision tree is just a flowchart of yes/no questions that ends in a guess. A single tree is weak — a rough guesser that makes lots of mistakes.

Boosting = a relay of trees, each fixing the last one's mistakes. Instead of one big tree, gradient boosting builds many small trees one after another. The trick: each new tree doesn't predict the answer from scratch — it only predicts the leftover error of all the trees before it.

Think of putting in golf: the first swing gets you most of the way (tree 1's rough guess); the ball is still short — that gap is the "error"; the next putt covers the remaining distance (tree 2); then you're a little off, and the next putt covers that. Each stroke handles only what is left over, and together they sink the ball.

Two terms fall out of this:

  • "Gradient" — at each step it figures out the direction that reduces the error the most, and steps that way (like always aiming at the hole).
  • "Learning rate" — how big each step is. Small, careful steps avoid overshooting.

The settings it uses (scikit-learn defaults):

100 trees each shallow — depth 3 learning rate 0.1

Lots of small, simple trees correcting each other. This kind of model is popular precisely because it is very good on spreadsheet-style data like yours.

What a single tree actually looks like

A common mix-up: "one GBR per stat" means each model predicts one stat — but every tree still reads all ~33 pre-match inputs to make that prediction. So the tree is not built from one stat; it asks questions about many inputs to guess one output. Here is one shallow tree from the model whose job is to predict HomeShots:

Two things to notice:

  • The questions are about the inputs (form, players, head-to-head, weather) — never about HomeShots itself. HomeShots is only the thing being predicted.
  • The leaf numbers are nudges, not final answers. A single tree never says "14 shots." It says "+0.4" or "-1.2" — a small correction. The model starts from the overall average and then adds up the nudges from all 100 trees:
final HomeShots = 12.5 (average) + tree₁ + tree₂ + tree₃ + … + tree₁₀₀

That is the golf-putt idea again: each tree covers a bit of the remaining error. And there is a separate forest of 100 trees for every stat — one forest for HomeShots, another for AwayXG, another for HomePossession, and so on.

How your project uses it, step by step

1 · One separate GBR per statistic. It does not build one model for everything. It loops over each target stat and trains a brand-new, dedicated GBR for each one.

Inputs (same ~33 for every model) Outputs (one model each)
Team form · Head-to-head · Player strength · Weather xG, shots, shots on target, possession, passes, pass accuracy, fouls, cards, corners, offsides

2 · It learns from past played matches. Those are the only games where it can see both the pre-match info and the real in-game stats that actually happened — that is how it learns the link between "what we knew before" and "what happened."

3 · The "5-fold out-of-fold" trick (honest self-grading). These predicted stats later feed BART, so the GBR must not be allowed to predict a training match it has already memorised (that would be overfitting). So for training rows it uses 5-fold cross-validation:

  • Split the played matches into 5 equal piles.
  • Train on 4 piles, predict the 5th (the one it did not see).
  • Rotate, so every pile is predicted by a model that never saw it.

No match is ever predicted by a model that already knew its answer. (For future matches it then trains on all the data and predicts those.)

4 · The median safety net. If a stat has too little history — fewer than 25 usable past matches, or every value is identical (nothing to learn) — it does not trust a model at all and falls back to the median (the typical past value). Better a safe average than a wild guess.

5 · Tidying up the raw numbers. A raw model can output unrealistic values, so a cleanup step:

  • Forces home + away possession to add up to 100%.
  • Rounds counts (shots, corners, cards) to whole numbers ≥ 0.
  • Caps percentages between 0 and 100.

Where it fits in the bigger picture

~33 pre-match inputs → GBR (one forest per stat) → predicted match stats → squeezed into the General signal → joins H2H + Player + weather → BART → goal difference → Win / Draw / Loss %

One reminder: the GBR only runs in "predicted" mode (used for future games). In the default re-test mode it uses the real stats instead, so the GBR is skipped there.

Model 2

Surrogate — Weight Picker (the full bottom-to-top picture)

The surrogate's whole job is to find good weights. So to understand it we follow the entire machine from a single random weight at the bottom, up to the score the surrogate learns from — then how the surrogate uses that score to pick better weights.

What problem is it solving? Every run uses a different weight setting (the dials). Trying one setting for real is slow — you must build the signals, train BART, and score it. There are far too many settings to test them all. The word surrogate means "stand-in": a fast stand-in that predicts how well a setting would score in a split second, so the program only runs the most promising ones for real.

The idea (simple version)

Think of a flight simulator. Flying a real test plane for every tiny tweak is slow and expensive. A simulator tuned on thousands of past flights can tell you "this configuration will probably fly well" in seconds — so you only take the best few into a real flight. The surrogate is that simulator, but for weight settings.

Part 1 — What the surrogate is optimising: from one weight up to a score

Before the surrogate can pick good weights, those weights first have to turn into a score. Here is that whole journey, bottom to top. Each layer takes the numbers from the layer below, transforms them, and hands the result up.

The two hand-offs where the weights actually bite:

GoalCreation = (0.7×1.4 + 2×0.84 + 5×1.2) / (1.4 + 0.84 + 1.2) = 8.66 / 3.44 = 2.52
General_BaseSignal = (0.55·GoalCreation + 0.30·GameControl + 0.15·Discipline) × BaseMultiplier_General

Two things to remember: the weights are born random at Layer 0 — nothing calculates them — and the weighted average at Layer 2 divides by Σw, so only the relative weights inside a subgroup matter; the base multiplier (Layer 4) sets the overall loudness.

Part 2 — What the surrogate does with that score (step by step)

Now the surrogate itself. It learns the pattern weight setting → score, then uses it to choose which settings are worth actually running. Its exact process each round:

The surrogate loop, sitting on top of the bottom-to-top stack.

Step 1 · Load the history. Read the run-history file and keep only valid, comparable rows: same stats-mode, source-mode and feature-schema, with non-empty scores.

Step 2 · Decide whether to use the surrogate. If fewer than 100 valid rows survive, skip it and just generate random settings (pure random search). Otherwise continue.

Step 3 · Train two stand-in models. One learns setting → AvgNLL, the other setting → Accuracy. The input is the full weight bundle plus the H2H value k.

Input (one full weight setting)Outputs (two separate predictions)
All per-feature dials + base multipliers + kPredicted AvgNLL (lower is better) · Predicted Accuracy (higher is better)

It models both because they can disagree — a setting can be accurate but over-confident, or well-calibrated but slightly less accurate.

Step 4 · Generate 300 random candidates. Each is just a fresh bundle of random weights (Layer 0) plus a random k.

Step 5 · Predict every candidate's score with the two models — milliseconds, no BART involved.

Step 6 · Select which to actually run, using two ideas:

  • Pareto front (best trade-offs). Picture the 300 guesses as dots on a chart (AvgNLL vs Accuracy). The Pareto front is the leading edge — settings where you can't improve one score without worsening the other. These are the exploit picks.
  • Exploit vs explore. 80% of the budget runs the Pareto-best (use what works); 20% runs purely random settings (so the search never gets stuck, and can find regions the surrogate hasn't seen).

Step 7 · Run only the chosen settings for real — that means sending each one up through Layers 0–8 (build signals → BART → probabilities → score).

Step 8 · Append the results to the history, so next round the surrogate trains on more data and picks better. Two details: history is always read from the reference folder; future-mode runs only become useful training data after they have been scored against real results (Stage 4 backfill).

Default engine: Gradient Boosting or a small Neural Net (64→32) needs ≥100 valid past runs 300 candidates per round 80% exploit / 20% explore

The default engine is itself a Gradient Boosting model (same family as Model 1) — but here it predicts scores of settings, not match stats.

Where it fits in the bigger picture

random weights → (Layers 1–7) → score → Surrogate predicts scores for 300 candidates → Pareto-best + random → run the winners for real → new scores → history → smarter weights next round

So the surrogate never predicts a match — it predicts how good a weight setting is, turning a blind, expensive search into a guided one.

Model 3

BART — Outcome Model (how the model is built)

Bayesian Additive Regression Trees — a sum of 200 small decision trees. What makes BART special isn't the trees themselves but how they are grown and re-grown: by splitting, pruning and resampling, over and over.

The core shape: BART's prediction is simply the sum of 200 small trees. Each tree reads the match's signal row and outputs a small nudge; the nudges add up to the predicted goal difference. Everything below is about how each of those trees is actually constructed.
prediction = tree₁ + tree₂ + tree₃ + … + tree₂₀₀

1 · The building block — a single tree (splits & leaves)

A regression tree is a flowchart of yes/no questions. Each question is a split: it picks one input and a threshold and divides the matches into two groups. At the bottom sit the leaves, each holding one number — the nudge for any match that lands there.

    A -->|no| B
    A -->|yes| C
    B -->|no| D

    C -->|no| F

One small tree: internal nodes are splits; leaves hold the nudge. A match follows the answers down to exactly one leaf.

2 · How a tree changes shape — the moves

BART never builds a tree once and freezes it. It keeps reshaping every tree with small random moves:

  • GROW — take a leaf and turn it into a new split (add detail). This is the "growth" step.
  • PRUNE — the opposite: remove a split and merge its two leaves back into one (simplify).
  • CHANGE — keep the shape but change a split's rule (a different input or threshold).
  • SWAP — swap the split rules between a parent node and its child.

A GROW move: one leaf becomes a split with two new leaves. PRUNE is this same picture in reverse.

3 · How BART learns — Bayesian backfitting (MCMC)

This is the big difference from the GBR. The GBR builds each tree once, greedily. BART instead loops over the trees again and again, gently improving each one with the moves above. One pass works like this:

flowchart LR
    R["pick one tree ·
compute its partial residual
(target − all OTHER trees)"]
    M["propose a move:
GROW / PRUNE / CHANGE / SWAP"]
    A{"accept?
(Metropolis rule)"}
    V["resample the leaf values
+ the error spread σ"]
    R --> M --> A
    A -->|usually, if it fits better| V
    A -->|sometimes reject| V
    V -->|next tree → repeat
for many iterations| R

The backfitting loop: each tree is re-fit only to what the other 199 trees can't yet explain.

  • Partial residual — before touching a tree, BART subtracts every other tree's output from the target. So each tree only has to explain the leftover the rest are missing.
  • Accept / reject — a proposed move that fits that leftover better (without making the tree too complex) is likely accepted; otherwise likely rejected. Occasionally a slightly worse move is accepted anyway, which lets BART escape dead ends.
  • Resample — the leaf numbers and the overall error spread σ are then drawn fresh from their probability distributions.
  • Repeat — this runs for many iterations. An early "warm-up" stretch is discarded; the rest are kept as samples.

4 · What keeps the trees small — the priors

Left unchecked, trees would grow huge and memorise the data. BART prevents this with built-in priors — gentle rules that favour simplicity:

  • Depth prior — the deeper a node, the less likely it is allowed to split. So trees stay shallow; each one is only a weak learner.
  • Leaf prior — leaf values are pulled toward zero, so no single tree can dominate the sum.

This is why 200 small, cautious trees beat one big tree: each captures a little, and together they are accurate without overfitting.

5 · The output — a prediction with built-in uncertainty

Because BART is probabilistic, it can express how unsure it is, not just give a point guess. In this project the predicted goal difference is taken as the answer, and the model's typical error on the training matches — the spread σ of its residuals — is used as the uncertainty. That σ is exactly what the next step needs to turn the single number into Win / Draw / Loss probabilities (a bell curve with a ±0.5-goal draw zone).

Where it fits in the bigger picture

signal row → BART: sum of 200 trees, each grown by GROW / PRUNE / CHANGE / SWAP inside an MCMC loop → goal difference + σ → bell curve → Win / Draw / Loss %

One note: BART is re-fitted for every weight setting the search tries — so in a single program run this whole MCMC procedure runs hundreds of times, once per candidate. The final "bell curve → Win / Draw / Loss %" step is only the default; it can be swapped for the score-distribution or draw-overlay modes described in the next section.

Layer

Outcome-Probability Conversion — goal difference → Win / Draw / Loss

Not a machine-learning model — a small, swappable layer that decides how BART's single number (goal difference) becomes three probabilities. This is the step where draw calibration is won or lost.

What problem is it solving? BART is good at picking the favourite but, like most goal-difference models, it systematically under-predicts draws — they sit in the messy middle. The probabilities the user actually bets against are produced here, after BART. So this layer is the lever for fixing draws without retraining anything. It is selected with one switch, OUTCOME_PROBABILITY_MODE, and the historical behaviour is the default.

Mode 0 · normal — the default (unchanged)

The original behaviour, kept as the default so nothing breaks: take BART's goal difference μ and its residual spread σ, lay a bell curve over them, and read off three slices using a ±0.5-goal draw zone.

Draw % = Φ((+0.5−μ)/σ) − Φ((−0.5−μ)/σ)  ·  Win % = 1−Φ((+0.5−μ)/σ)  ·  Lose % = Φ((−0.5−μ)/σ)

Everything below is opt-in: it runs only when a non-normal mode is chosen, re-mapping the probabilities after the scoreline (expected home/away goals) has been estimated.

Mode A · Score-distribution (Poisson & Dixon-Coles)

Instead of one bell curve over the goal difference, model each side's goals directly. Turn the expected home and away goals into two Poisson distributions, build the full grid of scorelines (0–0, 1–0, 2–1, …), and add the cells up into Home / Draw / Away.

P(home h, away a) = Poisson(h | λhome) · Poisson(a | λaway)  →  sum h>a, h=a, h<a

Dixon-Coles adds the well-known fix that plain Poisson gets wrong: it nudges the four lowest scorelines (0–0, 1–0, 0–1, 1–1) by a parameter ρ, which lifts low-scoring draws that Poisson alone undercounts. Two sub-flavours decide how aggressive to be:

ModeWhat it changes
score_poisson / score_dixon_colesReplace H/D/A entirely with the scoreline-grid probabilities.
score_poisson_draw_ratio / score_dixon_coles_draw_ratioBorrow only the new Draw %, then keep BART's original home : away ratio for the rest — a gentler nudge.

A blend weight α (0 → keep normal, 1 → full replacement) mixes the new probabilities with the default ones, and the row is renormalised to sum to 1.

Mode B · draw_multilayer_overlay — the bespoke draw lever

This mode never touches the favourite's identity — it only asks "how draw-ish is this match?" and raises the Draw % accordingly, taking the lift out of Home and Away in their existing ratio. The "draw-ishness" is a score in [0, 1] built from four similarity layers, each one high when the two teams look evenly matched:

    S2 --> SUP
    S3 --> SUP
    S4 --> SUP

Strength is the spine; score / stats / discipline only modulate it ±35%. The result is squeezed into a draw band (default 0.14–0.36) and blended in by α (default 0.60).

  • Strength — how close the teams are on the big signals (predicted goal difference, plus the General / H2H / Player base signals). Each uses an exponential closeness exp(−|home−away| / scale).
  • Score — a small expected goal gap and a low expected total (a 0–0-ish game is more drawable than a 3–3-ish one) via a total-goals cap.
  • Stats — similarity of the predicted match stats (xG, shots on target, shots, possession, pass accuracy, corners, passes), each with its own scale.
  • Discipline — similar fouls/cards and a "scrappy game" load term (lots of fouls/cards → choppier → more draw-prone).

The lift is one-directional and ratio-preserving:

final Draw = base + α·(max(base, candidate) − base)  ·  Home : Away keep their original split of the remainder

Guardrail — how a draw mode earns its place

A draw mode is only useful if it fixes draws without wrecking the rest. compare_draw_modes.py and eval_dixon_coles_all.py grade each mode per outcome (Home / Draw / Away log-loss) against the BWIN bookmaker across the backtested matchdays. The bar: lower Draw log-loss, no meaningful loss on Home/Away. Dixon-Coles can be re-scored exactly from saved expected goals, so it needs no BART re-run.

Where it fits in the bigger picture

BART → goal difference + σ → scoreline (expected home/away goals) → Outcome-Probability Conversion (normal · Dixon-Coles score dist · draw overlay) → Win / Draw / Loss % → scoring

Every run records which mode and parameters it used (OutcomeProbabilityMode, the DrawOverlay… / ScoreProbability… settings), and the surrogate history is filtered by them so only like-for-like runs are ever compared.
